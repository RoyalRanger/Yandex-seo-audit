# Чек-лист: технический SEO под Яндекс

Собран и проверен на spvrwa.ru, 2026-08-17, по 8 актуальным на тот момент страницам
support.yandex.ru/webmaster. **Перепроверяй актуальность формулировок при каждом
новом прогоне** (см. SKILL.md, правило №1) — Яндекс меняет требования без анонсов.

## 1. Что запрещено (правила отношений с поиском)

Нарушение этого раздела может привести к санкциям, а не просто к низкому месту —
проверяй в первую очередь, до любых технических улучшений.

- [ ] Никакого клоакинга (разный контент для робота и пользователя)
- [ ] Никакой мимикрии под другой сайт/бренд
- [ ] Никаких неожиданных для пользователя редиректов
- [ ] Никакого SEO-переспама текста (искусственно раздутая плотность ключей,
      нечитаемые для человека конструкции ради поисковика)
- [ ] Исходящие ссылки — только настоящие, ведущие на реальный релевantный контент,
      не биржи ссылок и не сети для накрутки

## 2. Технические требования (robot-technical-requirements)

- [ ] `robots.txt` на корне, отдаёт 200, не блокирует ничего важного для индексации
- [ ] `robots.txt` блокирует тонкие/дублирующие страницы: внутренний поиск
      (`/search`, `?q=`), админку, служебные пути
- [ ] `sitemap.xml` существует, указан в `robots.txt`, содержит реальные URL с
      `lastmod`, обновляется при публикации нового контента
- [ ] **IndexNow подключён** — ключ-файл отдаётся по `/<KEY>.txt`, уведомление
      (`indexnow_notify.py` или эквивалент) реально уходит в
      `https://yandex.com/indexnow` и встроено в деплой-процесс проекта
      (не разовый ручной запуск). Это часть базового набора для КАЖДОГО нового
      сайта на этом аккаунте, не опция "если попросят" — добавляй по умолчанию,
      даже если владелец явно не упомянул IndexNow в запросе на аудит.
- [ ] `favicon.ico` отдаётся с корня (`/favicon.ico`, не только `<link rel="icon">`
      с SVG/PNG) — Яндекс.Robot исторически не всегда подхватывает favicon только
      из тега, ищет файл на корне отдельно
- [ ] Сайт отвечает 200 без задержек на ключевые URL (главная, карточка/статья,
      категория)
- [ ] Мобильная версия работает (адаптивная вёрстка или отдельный мобильный URL),
      проверяется через `service/check-url`
- [ ] Если сайт за Cloudflare — проверь, не дублируется ли `User-agent: *` в
      финальном robots.txt из-за фичи Cloudflare "AI Crawl Control → Signals →
      Managed robots.txt" (дашборд Cloudflare, домен → AI Crawl Control →
      Signals). Когда она включена, Cloudflare сам вставляет в НАЧАЛО файла
      свой блок с `User-agent: *` + `Content-Signal: ...` + `Allow: /`, потом
      Disallow-блоки для известных AI-краулеров (GPTBot, ClaudeBot, CCBot и
      т.д.), затем маркер `# END Cloudflare Managed Content` — и уже после
      этого идёт origin-содержимое. Если origin ТОЖЕ пишет свой
      `User-agent: *\nAllow: /` (частый паттерн "по умолчанию") — получаются
      два таких блока подряд, и `Инструменты → Анализ robots.txt` в
      Вебмастере явно ругается: "Найдено несколько правил вида
      'User-agent: *'" (реальный кейс, signumcoin.ru, 2026-08-25). Фикс — в
      origin-конфиге НЕ писать свой `User-agent: *`/`Allow: /` вообще
      (Cloudflare-й блок уже покрывает всех обычных краулеров широким
      правилом), оставить только `Sitemap:`. Строку `Content-Signal:
      ...ai-train=no...` при этом Вебмастер тоже пометит как "неизвестная
      директива" — это ожидаемо (не входит в стандарт robots.txt, который
      знает Яндекс) и чинить нечем без отключения самой фичи в дашборде
      Cloudflare; отключение — решение владельца про политику AI-скрейпинга
      его контента, не чисто техническая правка, спрашивай прежде чем трогать.

## 3. Канонические адреса и дубли

Самая частая практическая проблема: один и тот же контент доступен по нескольким
URL (query-параметры пагинации, категории, трекинговые метки, случайные leaked
параметры типа `_ym_debug`), и каждый вариант индексируется отдельно, размывая вес.

- [ ] `<link rel="canonical">` на каждой странице
- [ ] Canonical строится по вайтлисту query-параметров, которые реально меняют
      контент (например `category`, `page`), а НЕ по принципу "убрать все
      параметры" или "оставить все параметры" — оба крайних подхода создают дубли
      или теряют легитимные варианты страницы
- [ ] Проверь реальные логи/Метрику на предмет "случайных" параметров, которые уже
      успели попасть в индекс как отдельные URL (реальный кейс: `?_ym_debug=2`
      от Яндекс.Метрики сам утёк в индексацию)

## 4. Структурированные данные (Schema.org / JSON-LD)

ИКС явно учитывает разметку Schema.org как один из факторов качества страницы.

- [ ] Статьи/новости — `NewsArticle` (или `Article`) с `headline`, `description`,
      `datePublished`, `image`, `author`, `publisher`, `mainEntityOfPage`
- [ ] Главная (или страницы с поиском по сайту) — `WebSite` + `SearchAction`,
      чтобы Яндекс мог показать сайтлинк-поиск
- [ ] Товар/услуга (для другого типа сайта) — `Product`/`Offer` с ценой и наличием
- [ ] Любой JSON-LD валиден: экранирован через штатный сериализатор шаблонизатора
      (`|tojson` в Jinja2), не собран руками через f-строки — иначе спецсимволы в
      заголовках/описаниях ломают JSON
- [ ] После деплоя — реально распарсить отданный JSON-LD (`json.loads`), не только
      визуально посмотреть

## 5. Метаданные и OpenGraph

- [ ] `<title>` уникален на каждой странице, отражает содержание, не дублируется
      между страницами
- [ ] `<meta name="description">` уникален, не пустой, не растянут на несколько
      экранов (короткое человеческое описание, не список ключевых слов)
- [ ] `og:site_name`, `og:type`, `og:title`, `og:description`, `og:url`, `og:image`
      — минимум для нормального превью при шаринге (влияет на CTR, косвенно на ИКС)

## 6. Индекс качества сайта (ИКС) — из чего складывается

ИКС явно учитывает: title/description/заголовки, наличие и качество Schema.org
разметки, мобильную оптимизацию, оригинальность контента, поведенческие факторы
(которые техническими правками напрямую не изменить — только качеством самого
контента и скоростью сайта). Технический аудит по этому чек-листу закрывает
факторы 2-5; поведенческие и контентные факторы — вне области этого скилла.

## 7. Инструмент проверки (service/check-url)

Не даёт советов сам по себе — показывает факты: HTTP-статус, мобильная
совместимость, что видит робот после рендера JS. Используй его, чтобы
верифицировать пункты выше на реальном сайте пользователя, если есть доступ к
подтверждённому в Вебмастере домену. Если доступа нет — верификация ограничена
`curl`/WebFetch снаружи, отметь это в отчёте пользователю как границу проверки.

Если сайт подтверждён в Вебмастере — открой не только check-url, но и
`Оптимизация сайта → Диагностика` (список рекомендаций/ошибок с реальными
датами) и `Индексирование → История обхода` (реальные HTTP-коды по URL,
которые видел робот) — это facts, а не предположения, и может вскрыть то, что
снаружи не видно (пример: "Страниц в поиске: 1" при 57 добавленных — сигнал,
что почти ничего не индексируется, даже если каждая страница по отдельности
отдаёт 200). UI Вебмастера у координатных кликов нестабилен (пункты меню
перестраиваются) — если координатный клик дважды промахнулся, ищи нужную
ссылку через `get_page_text`/явные href, не трать больше 2-3 попыток на
навигацию вручную.

**Обязательный под-шаг: "Страницы в поиске" → вкладка "Исключённые" → "Распределение".**
Не просто смотреть итоговое число "в поиске", а открыть разбивку исключённых страниц ПО
ПРИЧИНЕ (`?chartType=excluded&samplesType=distribution`). Там два принципиально разных
класса причин, требующих разного ответа:
- **Технические** ("Ошибка подключения к серверу", "Канонический адрес не указан",
  "Данные о каноническом адресе обрабатываются" и т.п.) — чинятся этим скиллом, и
  временный всплеск "обрабатывается" сразу после деплоя canonical-тегов — это ожидаемо
  (Яндекс переоценивает URL), не паниковать, должно само рассосаться за несколько дней.
- **Контентные** ("Малоценная или маловостребованная страница") — НЕ чинится техническим
  аудитом вообще, даже идеальным. Если эта причина покрывает заметную долю страниц (была
  145 из ~230 на spvrwa.ru) — это сигнал, что сама модель контента (короткие рерайты без
  полного текста источника, однотипная структура у сотен статей) читается Яндексом как
  тонкий/неуникальный материал, независимо от технической чистоты сайта. Смотри п.9 ниже.

**MCP `yandex-webmaster`** (если установлен, `npx yandex-webmaster-mcp`, github.com/altrr2/
yandex-tools-mcp) даёт этот же разбор напрямую инструментом `get-diagnostics`/через
агрегированные отчёты — быстрее браузерной навигации, используй его вместо координатных
кликов, если доступен.

## 8. SPA / client-side rendering — отдельный, более серьёзный риск

Если сайт — чистый SPA без SSR/пререндера (React/Vue/etc, `<div id="root">`
пустой в исходном HTML, весь контент и мета-теги приходят через JS), то ВСЁ
из пунктов 3-5 может технически существовать в коде, но реально не доходить
до робота, если тот не выполнил JS. Проверяется так: `curl` любую страницу,
не только главную — если HTML идентичен для всех путей (нет per-route
title/description/canonical в сыром ответе), это красный флаг.

YandexBot исполняет JS менее надёжно, чем Googlebot (который сам не идеален).
Открытый чек-лист этого скилла (пп. 3-5) остаётся правильным как список ЧТО
должно быть на странице — но КАК это туда попадает имеет значение:
клиентский `useEffect`, который дописывает `<head>` после гидратации,
может просто не увидеться роботом. Полноценное решение — SSR или
build-time пререндеринг статических HTML на маршрут; это архитектурное
изменение, выходит за рамки "не менять дизайн/контент" одного прогона
скилла — не делай его молча, спроси пользователя отдельно, стоит ли
браться (пример разговора: signumcoin.ru, 2026-08-22 — Вебмастер
подтверждённый, "Страниц в поиске: 1" из 57 добавленных, что похоже
на симптом именно этой проблемы, но чинить не стали в рамках техничного
прохода — только сообщили пользователю).

Частый конкретный баг на SPA (найден и пофикшен на signumcoin.ru,
2026-08-22): SEO-компонент типа кастомного `SeoHelmet` со значением по
умолчанию для `url`/`canonical` (например домашняя страница) — если на
внутренних страницах разработчик забыл передать проп с реальным путём,
canonical и og:url на ВСЕХ таких страницах молча указывают на главную.
Для робота это выглядит как "все страницы дубли друг друга" и может
объяснять то самое "страниц в поиске» намного меньше «страниц
добавлено». Всегда проверяй это explicitly — grep по всем вызовам
SEO-компонента на предмет отсутствующего `url`/`canonical` пропа.

## 9. Контентная глубина — за рамками технического аудита, но диагностируется здесь

Не паттерн для правки этим скиллом (см. "Область применения" в SKILL.md), но диагноз
ставится теми же инструментами (п.7 выше), поэтому фиксируется в чек-листе.

Массовое (не единичное) исключение по причине "Малоценная или маловостребованная
страница" — типичный симптом автоматизированных новостных/контентных конвейеров:
короткие (3-5 абзацев) рерайты чужих RSS-анонсов без выхода на полный текст источника,
десятки-сотни статей с одинаковой структурой и длиной. Технически у таких страниц может
быть идеальный canonical/JSON-LD/robots.txt — это не спасает, потому что причина не
техническая.

Реальный кейс (spvrwa.ru, 2026-08-24): 145 из ~230 статей исключены по этой причине,
хотя технический аудит (пп.1-6) был чист. Диагноз: рерайт шёл только с короткого RSS
`<description>`, не с полного текста статьи-источника. Владелец решил переписывать
контент отдельным проектом (см. SKILL.md, "Если владелец решает переписывать контент") —
не задача этого скилла реализовывать переписывание, только сообщить находку и дать
владельцу принять решение. Если пользователь спрашивает "как чинить" — можно упомянуть
как рабочую гипотезу (не навязывая): выкачивать полный текст источника, а не только
RSS-анонс; заметно увеличить глубину/объём; добавить нескопируемую точку зрения, а не
только пересказ факта — но конкретную реализацию делать только по запросу владельца,
это не автоматическое действие скилла.
